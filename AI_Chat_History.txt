================================================================
## Core Simulation Techniques
================================================================

----------------------------------------------------------------
### 1. Verlet Integration — Easy
----------------------------------------------------------------
The foundation of almost all rope/chain physics. Instead of tracking
velocity explicitly, you store the previous position and derive velocity
implicitly:

    new_pos = curr_pos + (curr_pos - prev_pos) * damping + acceleration * dt²

This is very numerically stable and naturally handles constraint solving.
Rain World uses this. Research: "Verlet integration game physics",
Thomas Jakobsen's classic GDC paper "Advanced Character Physics" (2001)
— free online, extremely relevant.


----------------------------------------------------------------
### 2. Distance Constraints (Constraint Relaxation) — Easy
----------------------------------------------------------------
Each pair of adjacent chain segments tries to maintain a fixed distance.
You iteratively "relax" them:

    delta = seg[i].pos - seg[i-1].pos
    correction = delta * (1 - rest_length / |delta|) * 0.5

Run this loop 3–10 times per frame for stability. This alone gives you
a basic tail. Research: "position-based distance constraints",
"Jakobsen constraints".


----------------------------------------------------------------
### 3. ECS Representation of a Chain — Easy-Medium
----------------------------------------------------------------
The key design question for your engine. Two approaches:
- One entity per segment with a ChainLinkComponent holding parent
  EntityId and rest length — fits your existing ECS well but adds overhead
- One entity with a ChainComponent holding a std::vector of segment
  positions — simpler, better cache behavior, harder to query per-segment
  for collision

Given your existing EntityId/generation system, the second approach
(one entity, array of points) is probably cleaner for a tail that
doesn't need individual entity logic.


----------------------------------------------------------------
### 4. Chain System as a New ECS System — Medium
----------------------------------------------------------------
You'd write a ChainSystem alongside your KinematicsSystem. It needs to:
- Read the root anchor (the player's body position)
- Apply Verlet integration to each link
- Solve distance constraints
- Write back positions for rendering

The tricky part: the root is kinematically driven (follows the player),
but the rest is physically simulated. You pin the first segment to the
player each frame after integration.


----------------------------------------------------------------
### 5. Angular Constraints — Medium
----------------------------------------------------------------
Distance constraints alone make the tail feel like a loose noodle.
Angular constraints limit how much adjacent segments can bend:

    angle between seg[i-1]→seg[i] and seg[i]→seg[i+1] < max_angle

Rain World uses this subtly to give the slugcat's body a more vertebrate
feel — it doesn't bend backwards sharply. Research: "angular constraints
Verlet", "bend constraints position-based dynamics".


----------------------------------------------------------------
### 6. Rendering the Chain — Medium
----------------------------------------------------------------
Options for drawing:
- Circles at each segment position (simplest, looks okay)
- Capsules between consecutive segments (more polished)
- Textured quads stretched between segments (sprite-based, Rain World style)

Your engine uses raylib, which has DrawLineBezier, DrawCircle, and raw
polygon drawing. The challenge is computing orientation per-segment to
align sprites. Research: "procedural rope rendering 2D".


----------------------------------------------------------------
### 7. Collision with Environment — Hard
----------------------------------------------------------------
Making the tail interact with platforms and walls is significantly more
complex:
- Each segment is a circle → use your existing CircleCollider type
- After constraint solving, push segments out of colliders
- Problem: this can cause constraint violations → need multiple solve
  passes interleaved with collision response
- The order of operations (integrate → collide → constrain vs.
  integrate → constrain → collide) matters a lot for stability

This is essentially the hard part of Rain World's system. Research:
"Verlet rope collision", "position-based dynamics collision response".


----------------------------------------------------------------
### 8. Inverse Kinematics (FABRIK) — Hard
----------------------------------------------------------------
Rain World uses this for limb placement (where feet land), not directly
for the tail. FABRIK is a forward-backward chain IK solver that's very
fast and stable. Only relevant if you want the tail to actively reach
toward or grab things. For a passive trailing tail, you don't need this.
Research: "FABRIK algorithm", "Aristidou FABRIK paper".

❯ I'm implementing a game project. How should I use git to organize tasks and features?

⏺ For a game project built on a hw skeleton, here's a clean approach:

  Branch strategy
  - main — always buildable, only merge when a feature is complete
  - dev — integration branch, merge features here first
  - feature/<name> — one branch per feature (e.g. feature/player-movement, feature/collision-layers)

  Commit discipline
  - One logical change per commit — "add gravity to kinematics" not "misc changes"
  - Commit when it compiles and the feature works, not every save
  - Prefix messages: feat:, fix:, refactor:, chore: (e.g. feat: add player jump with coyote time)

  For a hw-based project specifically
  - First commit: gut the .cpp files to stubs — chore: strip hw implementations to stubs
  - Tag that commit so you always have a clean rollback point: git tag skeleton

  Practical task flow
  1. Cut a branch: git checkout -b feature/enemy-ai
  2. Work, commit incrementally
  3. Merge to dev, verify it integrates, then merge dev → main

  What to put in .gitignore
  cmake-build-debug/
  cmake-build-release/
  .idea/
  *.o

  The .idea/ folder and build dirs are already in your repo — worth cleaning those out early before history gets long.

❯ what is difference between feature/name and dev?

⏺ dev is an integration branch — it's where you verify that multiple features work together before promoting to main.

  feature/<name> is isolated work — you don't know yet if it breaks other things.

  Flow:
  feature/player-movement  ──┐
  feature/collision-layers  ─┼──► dev ──► main
  feature/enemy-ai          ──┘

  Concrete example of why it matters:
  - feature/player-movement and feature/collision-layers each work fine alone
  - But when merged together, the player clips through walls — that bug shows up on dev
  - You fix it on dev (or back on a feature branch) before it ever reaches main

  For a solo project, dev is optional overhead — you can merge features directly to main and just be disciplined about only merging working code. Most solo game projects skip dev entirely and it's fine.

  The rule of thumb: add dev when you have multiple features in flight at the same time and want a place to shake out integration issues before main.

❯ explain tag the commit

⏺ git tag gives a named, permanent pointer to a specific commit — unlike a branch, it doesn't move.

  Creating a tag:
  git tag skeleton          # lightweight tag on current commit
  git tag -a skeleton -m "hw skeleton stripped to stubs"  # annotated, with message

  Why tag your skeleton commit:
  If you've been working for weeks and something breaks badly, you can instantly get back to the clean starting point:
  git checkout skeleton     # look at the state at that tag
  git diff skeleton         # see everything you've changed since
  git checkout skeleton -- engine_core/systems/KinematicsSystem.cpp  # restore one file

  Other useful tags for a game project:
  git tag v0.1-playable     # first time the game is actually runnable
  git tag submission        # what you turned in

  Listing and using tags:
  git tag                   # list all tags
  git show skeleton         # inspect the tagged commit

  The key difference from a branch: a branch tip moves forward with every commit, a tag always points to the same commit forever. Think of it as a bookmark in history.

❯ After a feature is done, do I need to do anything to that branch?

⏺ Yes, delete it once it's merged. The branch has served its purpose.

  # delete locally
  git branch -d feature/player-movement

  # delete on remote (if you pushed it)
  git push origin --delete feature/player-movement

  -d (lowercase) is safe — it refuses to delete if the branch isn't merged yet. Use -D only if you're sure you want to force-delete unmerged work.

  Why bother deleting:
  - Branch list stays clean — 20 dead branches makes git branch noisy
  - No confusion about what's active vs done
  - Merged code lives in main/dev history, nothing is lost

  A common workflow is to delete the branch right after the merge:
  git checkout dev
  git merge feature/player-movement
  git branch -d feature/player-movement

ASSISTANT:

## Static Platform Logic

A static platform is an immovable solid surface that dynamic bodies
(players, enemies) can stand on, collide with, or pass through.

### Core collision logic

The fundamental loop per frame:
1. Move the dynamic body by its velocity
2. Test for overlap with the platform's AABB (or shape)
3. If overlapping, resolve by pushing the body out along the axis of
   least penetration

    resolve_collision(body, platform):
        overlap = compute_overlap(body.bounds, platform.bounds)
        if no overlap: return

        # Push out on the shallowest axis
        if overlap.x < overlap.y:
            body.x += sign(body.x - platform.center.x) * overlap.x
            body.vel.x = 0
        else:
            body.y += sign(body.y - platform.center.y) * overlap.y
            body.vel.y = 0
            if body was moving downward: body.grounded = true

### Things to be aware of

Tunneling — fast-moving bodies can pass through thin platforms in a
single frame. Fix with swept collision (cast the body's movement as a
shape sweep) or sub-stepping.

Corner snagging — when a body slides along a surface it can get caught
on the edge of the next platform. Shrink the collision box slightly on
the sides, or add a small bevel radius.

Grounded detection — don't set grounded = true just because vertical
velocity was zeroed. A body sliding up the side of a platform also
zeroes vel.y. Check that the contact normal points upward (dot product
with (0,1) > some threshold).

Resolution order — resolve the Y axis before X, or vice versa, and
apply it consistently. Mixed order causes jitter at corners where two
surfaces meet.

One-way (pass-through) platforms — a common variant. Only resolve
collision if the body was above the platform in the previous frame and
is moving downward. Store prev_bottom for this check.

Floating-point precision — bodies resting on surfaces will drift due
to gravity accumulating each frame. Apply a small bias: if the body is
within 1-2px of a surface and moving toward it slowly, snap it flush
and zero velocity rather than tunneling through.

Moving vs. static — even if a platform doesn't move, structure your
collision code so the platform velocity is just (0,0). This makes
adding moving platforms later trivial.

### Minimal data a platform needs

    struct Platform {
        vec2 position   // top-left or center
        vec2 size       // width, height
        bool one_way    // pass-through from below
    }

Keep platforms as pure data with no behavior — your physics system
queries them. This separates concerns cleanly as the engine grows.

## One-Way Horizontal Platform

The entire mechanic reduces to a single guard condition: only resolve
collision if the player was above the platform surface last frame and
is moving downward.

### Per-frame logic

    before applying velocity:
        prev_bottom = player.y + player.height   # feet position last frame

    apply gravity and velocity:
        player.vel.y += gravity * dt
        player.y     += player.vel.y * dt

    for each platform:
        if not overlapping(player, platform): continue

        # The two conditions that must both be true to block
        coming_from_above = prev_bottom <= platform.top
        moving_downward   = player.vel.y >= 0

        if coming_from_above and moving_downward:
            player.y       = platform.top - player.height   # snap feet to surface
            player.vel.y   = 0
            player.grounded = true

The prev_bottom <= platform.top check is what makes upward
pass-through work — while jumping, the player's feet started below
the surface so the condition fails and collision is skipped entirely.

### Things to be aware of

Use prev_bottom, not current position — by the time you detect
overlap, the player has already moved into the platform. Checking the
current position would always be inside the platform and the condition
would be meaningless.

>= not > for downward check — include vel.y == 0 so a player resting
on a platform (gravity zeroed each frame) stays grounded and doesn't
slowly sink through.

Gravity accumulates before the check — apply gravity first, then
resolve. This means a resting player gets vel.y = gravity * dt each
frame, which gets zeroed by the snap. That's correct and keeps the
grounded check honest.

Snap, don't nudge — for one-way platforms, don't use penetration depth
to push the player out. Directly set player.y = platform.top -
player.height. Depth-based resolution can leave a tiny gap or overshoot
when the player falls fast.

Tunneling still applies — if the player falls faster than
platform.thickness / dt pixels per frame they skip past the surface in
one step. Since your platforms are horizontal and thin, use prev_bottom
(which you already have) as the starting point of a segment test
against platform.top:

    if prev_bottom <= platform.top <= current_bottom:
        # player's feet swept through the surface this frame

This is more robust than pure overlap detection and costs nothing extra.

Intentional drop-through — a common feel improvement is letting the
player press down to fall through. Implement this with a short-lived flag:

    if input.down and player.grounded:
        player.ignore_platforms_timer = 0.1s   # skip one-way checks for 100ms

### 1. Broad-phase X cull (almost free)

Skip any platform whose X range doesn't overlap the player's X range
at all. Most platforms in a level won't be under the player at any
given time.

    for each platform:
        if player.right < platform.left or player.left > platform.right: continue
        # now do the real check

This alone removes most candidates with two comparisons.

### 2. Track the current platform

When the player lands, store a reference to the platform they're on.
While grounded, you only need to verify they're still over it — a
simple X range check, no overlap math needed:

    if player.grounded:
        p = player.current_platform
        if player.right < p.left or player.left > p.right:
            player.grounded = false   # walked off the edge
            player.current_platform = null
        # no further collision checks needed this frame
    else:
        # do full sweep to find a landing

When grounded and still over the platform, you don't even need to
check Y — you know they're on the surface.

### 3. Spatial bucketing (if platform count is large)

Divide the world into vertical columns. Each platform registers into
the columns it spans. Only query the column(s) the player currently
occupies.

    columns[x_bucket(player.x)] -> list of platforms in that column

O(1) lookup instead of O(n).

### Practical advice

For most platformers, the platform count in any active area is small
(under ~50). The X cull + current platform reference is almost always
sufficient and keeps the code simple. Spatial structures are only
worth it if you have hundreds of platforms or a very large open world.

## The core idea

A one-way platform should only block the player when the player is:

- moving downward
- and crossing the platform’s top surface from above

If the player is moving upward from below, the overlap should be ignored.

So the problem is not “are these two things overlapping?”
The problem is “did the player arrive at this overlap from above or from below?”

That is the logic I derived from your code.

## How to decide above vs below

Just checking the current overlap is not enough.

Why: once two boxes overlap, the current positions alone do not reliably tell you whether the player:

- fell onto the platform from above, or
- jumped into it from below

You need motion context.

So the usual reasoning is:

1. Look at the player’s vertical velocity.
2. Reconstruct or remember the player’s previous vertical position.
3. Check whether the player crossed the platform top during this frame.

### Intuition

If last frame the player’s feet were above the platform top, and this frame the feet are at or below the platform top, then the player has landed on it.

If last frame the player’s head/body was below the platform and they moved upward into it, that should not count as a solid collision.

## Why velocity matters

Your physics updates position before collision detection. So by the time collision detection runs, the player may already be intersecting the platform.

To know whether that overlap should be resolved, you need to ask:

- was the player moving down?
- was the player above the top surface before the move?

If the answer is yes, keep the collision.

If not, remove that collision before the generic resolver sees it.

That is the basic approach.

## Why I would not put this in `CollisionSystem::separate`

Your `CollisionSystem` is currently generic. It just sees two overlapping AABBs and separates them symmetrically.

That is fine for normal solid objects.

But one-way platforms are not a generic geometric rule. They are a gameplay rule:

- only applies to certain layers
- only applies to player-vs-platform
- depends on direction of motion
- depends on previous frame state

That makes it better suited to the game layer, in your post-detection hook.

## The reasoning path I used on your code

I looked for three things:

1. **Where movement happens**
   - your kinematics system updates `vx/vy` and then `x/y`

2. **Where collisions are detected and resolved**
   - detection produces a list of overlaps
   - there is a game callback before resolution

3. **Whether the solver is direction-aware**
   - it is not; it just pushes overlapping bodies apart

From that, the conclusion is straightforward:

- the generic solver cannot distinguish “landed from above” from “jumped from below”
- so the overlap list must be filtered before resolution

That is where the one-way platform rule belongs.

## Functional outline

The implementation concept is:

1. Tag some colliders as one-way platforms.
2. Let normal overlap detection run.
3. For each player-platform overlap:
   - if player is falling and crossed the platform top from above, keep it
   - otherwise ignore it
4. Run the normal resolver on the remaining collisions.
5. After resolution, mark player as grounded if they landed on a platform top.

## Grounded state

You also need a grounded rule because jump logic depends on it.

A good grounded definition here is:

- player is grounded only when they are standing on the top face of a platform
- not when touching from below
- not when intersecting from the side

That follows naturally from the same landing test.

## Why “crossing the top surface” is the key test

This is the most stable rule because it solves common edge cases:

- jumping up through platform: ignored
- falling onto platform: solid
- already standing on platform: remains grounded
- walking off edge: no longer grounded
- brushing platform side while falling: not treated as landing unless top was crossed

That is why one-way platforms are usually modeled as “top-face only” surfaces, not as full solid rectangles.

## Design takeaway

The logic comes from separating two responsibilities:

- **collision detection**: tells you what overlaps
- **gameplay collision policy**: tells you which overlaps matter

One-way platforms are a collision policy problem, not a raw collision detection problem.

USER:
Are you sure FABRIK is not the most simple method?
----------------------------------------------------------------

ASSISTANT:
Yes, for a passive tail / rope-like chain, FABRIK is usually not the simplest method.

FABRIK solves: given a chain and a target point, bend the chain so the end reaches the target. That is useful for arms, legs, tentacles, or a tail tip deliberately reaching toward a switch.

Basic chain physics solves: given a chain attached to a moving body, let the rest of the chain naturally lag, swing, and settle. For that, Verlet + distance constraints is simpler because there is no target. You only need current point positions, previous point positions, fixed segment lengths, gravity/damping, and a root pinned to the player.

Short answer:
Passive swinging tail: Verlet chain is simplest.
Target-reaching tail: FABRIK is simplest.
Rain World-like body motion: start with Verlet, not FABRIK.

Phase 1: Minimal Data Model
Add a chain/tail representation. For the first version, one entity should own the whole chain, not one entity per segment.

Conceptually:

struct ChainPoint {
    float x;
    float y;
    float prevX;
    float prevY;
};

struct ChainComponent {
    EntityId rootEntity;
    std::vector<ChainPoint> points;
    float segmentLength;
    int constraintIterations;
    float damping;
};

Why this is simpler: the tail behaves as one object, does not require many ECS entities, constraint solving is easier in one array, and rendering can draw lines/circles between points.

Phase 2: Basic Verlet Update
Each frame:
1. Find the root entity, usually the player.
2. Pin point[0] to the player's position.
3. For every other point, compute velocity from current - previous, store current as previous, move by velocity * damping, and optionally add gravity.
4. Pin point[0] again.

Formula:

float vx = point.x - point.prevX;
float vy = point.y - point.prevY;
point.prevX = point.x;
point.prevY = point.y;
point.x += vx * damping;
point.y += vy * damping + gravity * dt * dt;

Phase 3: Distance Constraints
After Verlet integration, run constraint solving several times:

repeat 4-8 times:
    pin point[0] to player
    for each pair point[i - 1], point[i]:
        move them so their distance equals segmentLength

For a pinned root, point 0 is fixed, point 1+ can move, and for pairs after the root, split correction between both points.

Phase 4: Render It Simply
Start with debug rendering: draw circles at chain points and draw lines between neighboring points. Do not start with sprites.

Phase 5: Attach to Player
Initialize points trailing behind the player:
point[0] = player position
point[1] = player position - segmentLength on x
point[2] = player position - 2 * segmentLength on x
...

Then every frame, pin point[0] to the player. Chain update should probably happen after KinematicsSystem::update because the tail should follow the latest player position.

Phase 6: Only Then Add Gameplay Collision
For the flower/switch idea, do not collide the whole tail with the environment at first. Just detect whether chain points or chain segments overlap switches.

Suggested milestone order:
1. Draw a static chain attached to player.
2. Make chain points follow player with Verlet, no constraints.
3. Add distance constraints.
4. Add damping and gravity tuning.
5. Draw nicer circles/lines/capsules.
6. Add switch detection using tail points.
7. Optional: angular constraints.
8. Optional and hard: environment collision.

Reading order:
1. Thomas Jakobsen, Advanced Character Physics — Verlet and constraints.
2. A short tutorial on Verlet rope simulation.
3. Basic Position Based Dynamics distance constraints.
